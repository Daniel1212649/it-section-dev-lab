# Практика 03: вопросы про API

## Цель

Проверить, получается ли объяснить основные понятия API своими словами, а не
только узнать знакомые определения.

- [API №1: API - посредник между приложением и сервером](https://telegra.ph/CHast-1--API---posrednik-mezhdu-prilozheniem-i-serverom-06-19)
- [API №2: Как документировать, развивать и выбирать API](https://telegra.ph/API-s-nulya-CHast-2-kak-dokumentirovat-razvivat-i-vybirat-API-06-22)

## Задание 1. Вопросы на понимание

Создайте `solutions/03-api/api-questions.md` и ответьте на 15 вопросов. Для
каждого ответа достаточно 2–4 предложений.

1. Что такое API и зачем оно нужно?
2. Чем API отличается от пользовательского интерфейса?
3. Что называют контрактом API?
4. Кто такие client и server?
5. Чем consumer и provider отличаются от client и server?
6. Что такое endpoint? Приведите простой пример.
7. Из каких основных частей состоит HTTP-запрос?
8. Что сервер обычно возвращает в HTTP-ответе?
9. Чем синхронное взаимодействие отличается от асинхронного?
10. Когда асинхронное взаимодействие удобнее синхронного?
11. Чем публичное API отличается от внутреннего?
12. Для кого предназначено партнёрское API?
13. Зачем API нужна документация?
14. Чем OpenAPI отличается от Swagger?
15. Какие изменения могут нарушить обратную совместимость API? Приведите один
    пример.

## Критерии готовности

- ответы написаны своими словами;
- у примеров указаны участники взаимодействия;
- термины не объясняются через самих себя;
- файл оформлен в Markdown и легко читается;
- в конце записаны три вопроса, которые остались после выполнения.

## Задание 2*. OpenAPI-контракт

Спроектируйте API сервиса для сохранения ссылок:

```http
POST /links
GET /links
GET /links/{id}
PATCH /links/{id}
DELETE /links/{id}
```

Создайте файл `solutions/03-api/openapi.yaml` и опишите в нём:

- назначение каждого endpoint;
- path- и query-параметры;
- request body для создания и изменения ссылки;
- успешные ответы и их HTTP status codes;
- ошибки в едином формате;
- схемы данных для ссылки и ошибки;
- авторизацию через Bearer token.

Для `GET /links` добавьте простую пагинацию с параметрами `limit` и `offset`.
Продумайте, какие поля обязательны при создании ссылки, а какие можно изменить
через `PATCH`.

Откройте спецификацию через Swagger Editor или Swagger UI и убедитесь, что:

1. YAML разбирается без ошибок;
2. все пять endpoint отображаются;
3. request body, параметры и ответы связаны со схемами;
4. Swagger позволяет указать Bearer token;
5. примеры запросов и ответов понятны без дополнительных объяснений.

В `solutions/03-api/README.md` добавьте скриншот или короткую запись о
результате проверки и перечислите принятые проектные решения.
